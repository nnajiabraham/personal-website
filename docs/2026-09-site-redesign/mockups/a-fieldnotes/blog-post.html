Prompt promotion is a release, not a deploy

A prompt change can alter behaviour as much as a code change, but most teams ship it like a config edit. Here is the pipeline we settled on: pinned versions, an eval gate, and approvals that do not require production access.

  • agents
  • evals
  • ci-cd

Why “deploy” is the wrong frame #

A deploy moves an artifact you have already decided to trust. A prompt edit changes what the artifact does. When we treated prompts as configuration, three things happened within a quarter: an approver waved through a change they could not evaluate, a rollback restored code but not the prompt, and nobody could say which prompt produced a given trace.

Treating promotion as a release fixes all three, and it costs one extra YAML file per agent.1

Pins #

Every environment references prompts by an immutable version, never by latest. The pin file is committed next to the agent and reviewed like code:

yaml 
# prompts.pins.yaml — reviewed, never hand-edited in prod
agent: underwriting-classifier
environments:
  staging:
    system: "sys@v14"
    candidate-selection: "cand@v7"
  production:
    system: "sys@v13"   # promoted 2026-08-21, eval run 4412
    candidate-selection: "cand@v7"

The highlighted lines are the only ones a promotion PR touches. That makes the diff legible to someone who has never opened the prompt.

Why not a database row?

We tried it. A row has no reviewer, no diff, and no blame. Git already does all three; the pipeline just had to stop pretending prompts were special.

The eval gate #

A promotion PR triggers the eval runner against the candidate pins. The gate compares to the current production pins on the same golden set and blocks the merge if any category regresses beyond its threshold.

CategoryMetricThresholdBlocking
Correctnessexact match on golden set−1.0 ptyes
Refusalsfalse-refusal rate+0.5 ptyes
Formatschema-valid outputs−0.0 ptyes
Latencyp95 end-to-end+15%warn
Costtokens per task+10%warn

Two honest notes. First, thresholds are within run-to-run noise on small sets; we quote the larger-sample headline and treat single-run wins with suspicion. Second, “warn” categories were “blocking” for a month and taught us nothing except how to click override.

Do not gate on a metric you cannot reproduce locally

If the eval only runs in CI, authors will stop reading it. The runner is a one-line make target and the golden set is in the repo.

Approvals without production access #

The approver sees the pin diff, the eval report, and three side-by-side sample outputs. They do not see production, and they do not need to. This is the enablement framing: the gate is the thing that made it possible to say yes to more people approving.

Nothing argues against the direction; three things argue against rolling out as-is.

That sentence, from a review, became the template for every promotion comment. Direction and readiness are separate questions.

What it cost #

  • One pins file per agent and a 40-line schema.
  • An eval runner we already had, made to accept two pin sets.
  • Roughly a day of arguing about thresholds, which was the useful part.

Reversible first step, stated migration path: if this turns out to be wrong, delete the pins file and you are back to config edits. We have not wanted to.

  1. Plus an eval run per promotion, which is the real cost. Budget for it. ↩
